# Развёртывание Telegram + MAX Support Desk через PM2

**Универсальный пример установки раннего прототипа.** Один Telegram-бот для клиентских диалогов, рабочей супергруппы и администрирования; один MAX-бот для своих клиентов. Общая PostgreSQL-база. В супергруппе каждому клиентскому аккаунту соответствует отдельная тема. Несколько менеджеров могут отвечать одновременно и клиент всегда видит только имя бота компании.

> Проект прошёл локальные тесты с имитациями Telegram и MAX API. Реальные сообщения и медиа на действующих аккаунтах платформ пока не проверены. Нужны токены, верифицированный MAX-бот, рабочая Telegram-супергруппа и HTTPS-сервер. Не публикуйте реальные токены в GitHub.

## Структура

```text
app/
  config.py        настройки из .env
  models.py        таблицы и версии материалов
  platforms.py     Telegram Bot API и MAX Bot API
  service.py       переписка, темы, менеджеры, администрирование
  main.py          два webhook, обработчики очередей, напоминания
scripts/
  register_webhooks.py   регистрация webhook на платформах
tests/
  test_core.py
  test_api.py
ecosystem.config.cjs  конфигурация PM2
nginx.conf.example     пример HTTPS reverse proxy
.env.example
```

## Реализовано

- Telegram: `/start`, меню «Материалы», «Написать менеджеру», прием сообщений, фото, документов и видео.
- MAX: приветствие после `bot_started`, выдача материалов, кнопки, прием сообщений и поддерживаемых медиа.
- Автоматическое создание темы при первом обращении, повторное использование темы, карточка с кнопками управления.
- Ответы всех авторизованных менеджеров через одну тему без блокировки других сотрудников; у клиента нет имён менеджеров.
- Поиск зарегистрированных клиентов по имени и ID, создание темы менеджером до первого клиентского вопроса.
- Статусы «Новая», «В работе», «Ожидание», «Закрыта»; автор ответов фиксируется в журнале.
- Админ-бот: изменение приветствия, добавление текста, ссылок, PDF, фотографий и видео, изменение порядка, удаление, редактирование текста, просмотр, публикация версии, возврат к предыдущему комплекту.
- Очередь исходящих сообщений с повторными попытками; защита от повторных webhook по ID; сохранение данных после перезапуска.
- Уведомления о новых обращениях, напоминания через 10 и 20 минут, сообщения о постоянных ошибках доставки.

## 1. Создание ботов и группы

1. В Telegram через официальный `@BotFather` создайте **одного** бота. Сохраните токен.
2. Создайте **закрытую Telegram-супергруппу**, включите **Темы**. Добавьте бота администратором с правами на управление темами и отправку сообщений. Сотрудники должны быть участниками группы, но их Telegram ID необходимо также разрешить в боте.
3. Получите ID супергруппы (число вида `-1001234567890`). До подключения webhook можно отправить сообщение в группу и выполнить `https://api.telegram.org/bot<TOKEN>/getUpdates`, найти `message.chat.id`. Токен нельзя вставлять в публичные документы и скриншоты.
4. Получите Telegram ID администратора, например после личного сообщения боту через тот же `getUpdates` (`message.from.id`).
5. Создайте MAX-бота через предусмотренную платформой процедуру для верифицированного профиля и получите токен. Убедитесь, что у него есть доступ к Bot API.

## 2. Настройки

```bash
cp .env.example .env
```

Откройте `.env` и заполните:

- `TG_BOT_TOKEN` — токен Telegram.
- `TG_GROUP_ID` — ID супергруппы.
- `TG_WEBHOOK_SECRET` — длинный случайный секрет только из букв, цифр, `_`, `-`.
- `MAX_BOT_TOKEN` — токен MAX (необязателен до подключения MAX).
- `MAX_WEBHOOK_SECRET` — длинный секрет для MAX.
- `PUBLIC_BASE_URL` — публичный HTTPS-адрес сервера, **без слеша в конце**.
- `ADMIN_IDS` — Telegram ID администраторов через запятую.
- `DATABASE_URL` — строка подключения к локальному PostgreSQL; пароль берётся из неё. 

При запуске через PM2 используйте реальный пароль пользователя PostgreSQL в `DATABASE_URL` с хостом `127.0.0.1`. Если пароль содержит специальные символы, их необходимо URL-кодировать. Пароль в `.env` должен быть конфиденциальным; файл исключён из Git.

## 3. Запуск через PM2 на Linux VPS (без Docker)

Подготовьте сервер с Python 3.11+ (версию проекта тестируйте на вашем дистрибутиве), Node.js + PM2, PostgreSQL и Nginx. Команды ниже выполняются **из папки проекта**.

### 3.1. Python и зависимости

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

Убедитесь, что в `.env` заполнены `TG_BOT_TOKEN`, `TG_GROUP_ID`, `ADMIN_IDS`, `MAX_BOT_TOKEN`, `PUBLIC_BASE_URL`, оба секрета webhook и `DATABASE_URL`. Для локального PostgreSQL строка начинается с `postgresql+psycopg://...@127.0.0.1:5432/...`.

**PostgreSQL должен быть установлен и запущен отдельно** (обычно `systemctl status postgresql`). Создайте пользователя `support`, базу `support` и установите пароль в `DATABASE_URL`. Не подключайте приложение к суперпользователю `postgres`.

### 3.2. Проверка и запуск процесса

```bash
.venv/bin/python -m pytest -q
pm2 start ecosystem.config.cjs
pm2 status
pm2 logs tg-max-support
curl http://127.0.0.1:8000/health
```

Ожидаемый ответ: `{"status":"ok"}`.

Чтобы PM2 восстанавливал приложение при перезагрузке VPS:

```bash
pm2 startup
# Выполните команду sudo, которую напечатает PM2
pm2 save
```

Обновление после изменений в коде:

```bash
.venv/bin/pip install -r requirements.txt
pm2 restart tg-max-support
```

**Не включайте cluster mode, `instances > 1`, `--reload` или несколько копий бота:** в текущем прототипе есть фоновый обработчик очереди, рассчитанный на один процесс.

### 3.3. HTTPS через Nginx

Публичный webhook обязан использовать HTTPS с доверенным TLS-сертификатом. Настройте DNS A/AAAA на ваш VPS и получите сертификат (например, Certbot). В `nginx.conf.example` замените `bot.example.com` на ваш домен и укажите правильные пути к сертификату. Прокси направляет HTTPS-трафик на `127.0.0.1:8000`.

Проверка после настройки:

```bash
sudo nginx -t && sudo systemctl reload nginx
curl https://bot.example.com/health
```

Регистрация webhook **после** успешного запуска HTTPS и настройки обоих токенов:

```bash
.venv/bin/python -m scripts.register_webhooks --platform all
```

Если MAX ещё не активирован, выполните `.venv/bin/python -m scripts.register_webhooks --platform tg`. Для MAX используйте `--platform max` после получения токена.

## 4. Начальная настройка администратора

В Telegram откройте личный чат с ботом и отправьте `/admin`. Бот предложит команды:

- **Приветствие** — изменение текста первого сообщения.
- **Добавить текст / ссылку / файл** — формирование черновика материалов.
- **Черновик** — просмотр материалов, кнопки `↑`, `↓`, «Удалить» и «Редактировать» для текста/ссылок.
- **Предпросмотр** — посмотреть последовательность в своём чате.
- **Опубликовать** — выпустить комплект для новых клиентов.
- `/versions` — показать сохранённые версии для возврата к одной из них.

Укажите менеджеров командами:

```text
/add_manager 123456789
/del_manager 123456789
```

Менеджеры смогут искать зарегистрированных клиентов в личном диалоге с ботом:

```text
/find Иван
/find 123
```

Затем нажмите «Открыть диалог» и ссылку на тему. Ответ в этой теме уйдёт клиенту. Менеджер не должен отвечать на служебные сообщения самого бота.

Служебные темы «Новые обращения» и «Управление» создаются автоматически после запуска, если у бота достаточно прав.

## 5. Пример взаимодействия

1. Клиент в MAX нажимает «Запустить» — получает приветствие и опубликованный комплект материалов.
2. Клиент пишет: «Здравствуйте, хочу уточнить цену».
3. Telegram-бот создает тему `MAX | Имя | #ID` и публикует сообщение клиента.
4. Любой из 3–5 менеджеров может нажать «В работу»; остальные всё равно могут отвечать.
5. Анна и Сергей пишут два сообщения в одной теме; клиент видит два обычных сообщения от бота компании.
6. Когда клиент задаёт вопрос снова, используется та же тема.
7. Если ответа нет 10 и 20 минут, появляются напоминания.

## 6. Тестирование

На локальном компьютере:

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
pytest -q
```

Тесты используют SQLite без внешних подключений. При запуске через PM2 в production используется PostgreSQL, установленный отдельно.

## Ограничения текущего прототипа

- **В production пока не проверен:** сетевые контракты необходимо протестировать на реальных Telegram и MAX ботах после выдачи токенов. Локальные тесты используют имитацию ответов API.
- Для загрузки файлов из Telegram ботом применяется ограничение **20 МБ** (стандартный `getFile`), а формат MAX должен быть совместим с их API; большие видео и некоторые голосовые форматы могут потребовать отдельного транскодирования или другого способа загрузки.
- При передаче медиаконтента MAX → Telegram используются URL вложений MAX. Если URL истёк либо недоступен Telegram, доставка завершится ошибкой; для строгой надежности необходимо добавить безопасное скачивание с проверкой URL и повторное получение актуальной ссылки.
- Восстановление процесса очередей предусмотрено, но **внешние API не дают гарантии exactly-once**: при разрыве сети сразу после успешной отправки возможен дубликат при повторной попытке.
- Нет фоновой проверки истечения MAX webhook-подписки; если её отменит платформа, регистрацию нужно повторить. Рекомендуется добавить мониторинг подписки и алерты.
- Нет отдельной админ-страницы и биллинга. Роли ограничивают отправку через бота, **не видимость тем внутри супергруппы**.
- Архивирование и срок хранения персональных данных, удаление по запросу клиента, ротация ключей и тесты восстановления резервных копий необходимо определить до продуктивного внедрения.
- Для удобства одного FastAPI-сервиса оба мессенджера подключены напрямую к официальным Bot API через `httpx`; **aiogram пока не используется**, хотя предусматривался в исходном ТЗ. При необходимости можно выделить Telegram-адаптер на aiogram без изменения базы и общей бизнес-логики.
- Текущая реализация использует одного фонового обработчика и **один процесс Uvicorn**. Не запускайте несколько копий с одной БД без механизма распределённых блокировок и миграций.
